# Organizer App

The CourtSync web application. **An informational shell, not a working product yet** — Next.js 16, App Router, Tailwind v4.

One app serving three personas, one per format: a **tournament organizer** running a one-day event, a **league convener** running a season, and a **drop-in host** running a recurring session. They share the same material — courts, time slots, participants, matches — but work at very different rhythms. Full detail in [PRODUCT.md](../../PRODUCT.md).

## What exists today

A landing page (`/`) and one area page per persona (`/tournaments`, `/leagues`, `/dropins`), sharing a design system built around the product's own artifact — the court × timeslot schedule grid, rendered at each persona's actual rhythm (dense one-day grid, repeating weekly strip, live rotating row). No database, no auth, no forms that submit anywhere. Every persona's copy in `src/lib/personas.ts` — including the "built" vs. "being built" status shown on each area page — should stay honest and in sync with [PRODUCT.md](../../PRODUCT.md)'s Evidence on Hand section: nothing here presents invented data or unbuilt functionality as real.

```bash
pnpm dev   # localhost:3000
```

## Before the functional build starts

Two things block turning this from a shell into a product:

1. **Choose an auth library.** The database is settled — Neon serverless Postgres — but Neon ships no auth, so this is still open and it blocks every mutating path ([docs/DECISIONS.md](../../docs/DECISIONS.md)). Hand-rolling it is not an option; that is exactly what produced findings C1 and C2.
2. **Implement the scheduling package.** An app with no schedule generation has nothing to show an organizer beyond what already exists here.

Build for one persona's actual functionality first — see [docs/DECISIONS.md](../../docs/DECISIONS.md) for the argument that the drop-in host produces the fastest feedback loop. All three at once means finishing none.

## Authorization is the review gate

Neon has no row-level security to catch a missed check, so application code is the entire defence. Every mutating server action calls its authorization check as the **first statement**, with no exceptions — a route matcher is not a boundary, because Next.js registers server action ids globally.

## Reference, not a source

`scoopvolleyball` is a useful reference for app structure, admin flows and score entry. It is **not** a source to copy from — see [docs/PITFALLS.md](../../docs/PITFALLS.md) for what went wrong in it, particularly C1 and C2 on authorization.

## Notes for future sessions

- `AGENTS.md` / `CLAUDE.md` in this directory are auto-generated by `next dev` on every run, pointing at the Next.js docs bundled in `node_modules` for this exact version. They are committed on Next's own recommendation (its regenerate-on-dev behaviour otherwise just shows up as an uncommitted diff every session) and layer onto, not replace, the root [CLAUDE.md](../../CLAUDE.md).
- `next-env.d.ts` is **not** committed. Next rewrites it on every run and writes it differently for `dev` (`.next/dev/types/…`) than for `build` (`.next/types/…`), so tracking it means a phantom diff after every command. Next's own `create-next-app` gitignores it for the same reason, and `pnpm typecheck` passes without it.
- The design identity is deliberately single-theme (dark, "gym at night") rather than light/dark — a legitimate choice for a pre-launch marketing shell, not an oversight. See the comment at the top of `src/app/globals.css`.
